# The order-to-completion agent

The agent owns every order a doctor wrote for a patient, from the moment the
engine reads it until the engine says it is done. It talks to the patient on
WhatsApp, books what the doctor ordered, collects results the patient already
has and hands the rest to the clinic team. Decision record:
[ADR 0008](../adr/0008-order-to-completion-agent.md).

> **The agent acts, the engine verifies, the doctor decides.** The agent never
> marks an order fulfilled: it writes FHIR (an `Appointment`, an
> `Observation`) through the same ingestion as `POST /fhir`, and the
> deterministic engine decides what that fulfills. Findings and questions go
> to the doctor; nothing about a result goes to the patient.

## What the agent owns

Only the doctor's orders: expectations of the `doctor_plan` layer (read from a
note) and the universal rules that are orders or their direct consequence
(`lab_order_result_pending`, `imaging_order_result_pending`,
`short_treatment_followup`, `abnormal_result_followup`). Protocol and cadence
items are the engine's suggestions: the agent never pursues them (no demand
generation), and `list_open_orders` does not show them. An order is pending
while its expectation is `open` or `expired` (grouped into a case that can
still close late). `abnormal_result_followup` and critical items are urgent.

**The doctor confirms what the engine asked for.** `abnormal_result_followup`
is the engine's own order (an abnormal result asks for a visit), not
something the doctor wrote. It waits as `awaiting_doctor`
(`needsDoctorConfirmation`): `list_open_orders` does not show it, every tool
refuses it, no message or ladder rung is about it, and the doctor gets a
high-priority notice ("Abnormal result: confirm a follow-up visit?",
`confirm_followup`) in "For the doctor" and the staff tasks. The doctor's
confirmation (`POST /api/demo/agent/patients/:id/orders/:orderId/confirm`,
`OrderAgentService.confirmOrder`) is recorded on the order with the doctor's
id (the evaluator's email in a lab clinic) and the clinic's time
(`doctorConfirmation`, trace event `order_confirmed_by_doctor`); only then
does the agent start on it: the urgent track (trigger `doctor_confirmed`,
rung `urgent:0h`).

## Guardrails (all in code)

| Guardrail                  | Where                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Only doctor's orders       | `isAgentOwned`; every tool that takes an `orderId` refuses anything else (`not_an_open_order`).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| No result, no diagnosis    | `checkOutboundText` on the whole text of every outbound message (the model's words and the slot list code appends): see [What a patient message may say](#what-a-patient-message-may-say). A refused message is traced and the model must rewrite it. Values from a photo are never returned to the model.                                                                                                                                                                                                                                                                                                     |
| Dates and slots            | Only from `availableSlots` (the treating professional's or a lab's synthetic schedule, the clinic's time zone, never within 18 h, urgent orders within 7 days). `propose_slots` appends the list itself; ids are validated against the schedule (`slotFromId`). Every offer carries two or three slots (PRD V1-D): an offer of one is topped up by code (`slots_topped_up`), and a `send_message` that is an outreach or asks the patient to pick a time (`asksToBook`) with no offer in the turn gets two or three slots attached by code, skipping the weekdays the patient just refused (`slots_attached`). |
| Booking                    | `checkBookingConfirmation`: the confirming message must be the patient's latest text or voice message (a photo after it keeps the yes), the slot must be in the latest offer for that order and still free, and the message must be an explicit yes that singles out one slot when several were offered. A tentative reply ("quizás", "maybe", "déjame ver") is never a yes; "ok" to several options is not a choice; "ok" with no offer books nothing. One booking per confirming message (unique constraint) and per slot.                                                                                   |
| Contact policy             | `contactPolicy`, per patient whatever the number of orders: at most 2 proactive messages per patient per rolling 7 days; one proactive message per outreach (a turn that is not answering the patient writes once, and that message covers every open order: a second one is refused, `outreach_already_sent`); a message within 24 h of the patient's last message is a reply (at most 3 per patient message); nothing while the phone is undelivered.                                                                                                                                                        |
| Opt-out                    | `isOptOut` on every text and every transcribed voice note (code, not the model). Then nothing goes out again: no turn runs, no ladder rung fires, a fixed phone restarts nothing; open calls to the patient are withdrawn and the doctor gets a notice (an opt-out stops every patient contact, calls included, as the engine's own contact policy does, `docs/integration.md`); the engine records it as a FHIR `Consent` (deny, `follow-up-opt-out`), so its escalation goes to the coordinator. The orders stay open for the clinic to decide.                                                              |
| Pseudonymous model context | The model never sees the patient's name or phone: it writes `{first_name}` and code fills it in; patient names are masked (`patientRedactTerms`) in everything sent to a model.                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Budget                     | Every call through `llm_gateway`; lab clinics fall back to `DEMO_LLM_MONTHLY_BUDGET_USD`. A live turn that hits the budget re-runs on the scripted player and the trace says so.                                                                                                                                                                                                                                                                                                                                                                                                                               |

## What a patient message may say

A WhatsApp message can be read by anyone holding the phone, on a lock
screen or a shared device. So a message to the patient says what to do
and when, never what anything means. `checkOutboundText`
(`packages/core/src/engine/order-agent/outbound-safety.ts`) refuses a
message with any of these, folded (case and accents ignored) and matched
as whole words, on the whole text the patient would receive:

| Never                                      | Kind               | Examples refused                                                                                                                                                      |
| ------------------------------------------ | ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A measured value                           | `result_value`     | "8,4 %", "8.4", "138 mg/dL", "95 por ciento", "ocho coma cuatro", "eight point four"                                                                                  |
| A verdict on a result, good or bad         | `result_judgement` | "alto", "salió alta", "elevado", "normal", "fuera de rango", "empeoró", "preocupante", "buenas noticias", "high", "within range", "worse", "concerning"               |
| A condition, or a word that stands for one | `condition_term`   | every condition term of the note extraction's tables (both languages: "diabetes", "DM2", "hipertensión"…), and "el azúcar", "la presión", "your sugar", "the thyroid" |
| The name of a test or study                | `test_name`        | every term of the lab-test lexicon `TEST_GROUPS`: "HbA1c", "hemoglobina glicosilada", "glucosa", "perfil lipídico", "PSA", "VIH", "Pap", "mamografía"…                |
| The word diagnosis                         | `diagnosis_word`   | "diagnóstico", "diagnosed"                                                                                                                                            |
| Treatment instructions                     | `medical_advice`   | "aumenta la dosis", "stop taking"                                                                                                                                     |

**Test names are never allowed**, alone or not: a test's name says what it
monitors (an HbA1c is diabetes, a PSA the prostate, a VIH test HIV), and
code cannot tell a neutral test name from a revealing one. An order is
named by its generic category only, which `list_open_orders` gives the
model as `patientWording`: "un control" / "a follow-up visit", "un examen
de laboratorio" / "a lab test", "un estudio de imagen" / "an imaging
study". The test's own name (`test`) is for the model and the clinic team
only (the order list, staff tasks, the doctor's panel). A few lexicon
entries that are everyday words or chat shorthand ("k", "echo", "placa")
are not treated as test names; the test's full name still is.

Allowed: what to do and when ("tu médico te pidió un control y un examen
de laboratorio", "¿te sirve el jueves a las 9:30?"), that a result was
received and that the doctor will review it, and the slot list (clock
times are not values). Proven by
`packages/llm/src/agent/outbound-safety.property.test.ts` (every scripted
template and slot line passes; every test name, condition term, value and
verdict is refused in every frame; 3 000 generated adversarial messages are
refused with every leaked kind reported) and
`apps/api/src/agent-guardrails.test.ts` (an adversarial model's leaking
messages are refused by the toolbox and never stored).

## Tools

`list_open_orders`, `read_patient_summary`, `get_contact_policy`,
`get_available_slots(orderId, preference, excludeWeekdays)`,
`send_message(text)`, `propose_slots(orderId, slotIds, text)`,
`create_appointment(orderId, slotId, confirmationMessageId)`,
`match_result_to_order(messageId)`, `submit_fhir_result(orderId, messageId)`,
`create_staff_task(reason)`, `end_turn(summary)`. One tool per step, arguments
validated with zod. A model that answers in prose after acting is reminded of
the protocol once (`prose_reminded`); a second time ends its turn. A live
outreach turn (first contact, a rung, a confirmation, a fixed phone) that
ends without writing, when the contact policy allows it and an order is
still being chased, is backed by the scripted player for that turn
(`outreach_fallback_scripted`): the ladder's timing is code.

## A result from a photo

The vision model reads the photo into `{ isLabReport, reportDate,
patientName, tests: [{ name, value, unit, referenceLow, referenceHigh }] }`
(trace: `photo_read`). `match_result_to_order` maps each test name to the
lab-test lexicon (`TEST_GROUPS`) and to a pending test order with the same
LOINC group, and compares the printed name with the patient's.
`submit_fhir_result` builds a `final` `Observation` (LOINC, value, UCUM unit,
reference range, interpretation `H`/`L`/`N` computed by code, the report's
date) and ingests it. The engine closes the expectation (`expectation_fulfilled
… by Observation/…`) or not (`expectation_still_open`). An `H` or `L` result
runs the clinical reviewer on the clinic's clock: the findings (a lab trend,
a pre-visit question about it) go to the doctor, in the clinic's flag modes
(shadow in a lab clinic).

## The no-response ladder

Timing is code (`LADDER`, offsets from the track's anchor on the clinic's
clock); the model only words a message rung within its brief. A patient's
reply pauses the ladder; the agent's next message re-anchors it.

| Track       | Rungs                                                                                                                                                                                                                                      |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| routine     | day 0 message with two slots · day 4 two other times · day 9 remove friction (Saturday, the nearer lab) · day 14 call task for reception (three-line summary) · day 21 unreachable: orders stay open, retry in 30 days, the doctor is told |
| urgent      | hour 0 slots this week · day 1 other hours · day 2 high-priority call task · day 3 the doctor directly · day 7 unreachable, flagged for the next contact                                                                                   |
| undelivered | at once: stop messaging, same-day task to update the phone · day 7 call via other contact data · day 14 unreachable. "Reception updated the phone" restarts the previous track.                                                            |

The ladder runs as the `order_agent.ladder` worker job, day by day over the
span the clock crossed: a lab clinic's date jump (`setLabClinicDate`)
schedules it, and the hourly sweep does for real clinics. Message rungs run a
full agent turn inline at that day's instant.

## Trace

Every step is an `AgentStep` (stored in `order_agent_steps`, ordered by
`seq`) with `kind` (`model`, `tool`, `engine`, `transcription`, `vision`,
`guardrail`, `ladder`, `policy`), `tool`, sanitized `arguments` (short
strings, numbers, string lists), `read` (sources: `expectations`, `schedule`,
`message:<id>`, `vision_reading`…), the model's stated `reason`, `outcome`
(`ok`, `rejected`, `error`, `info`), a stable `event` code with scalar
`params` (rendered by the console in the reader's language), and for model
calls `model`, `costUsd`, `latencyMs`, `inputTokens`, `outputTokens`. Runs
(`order_agent_runs`) sum model calls, tokens and cost per turn.

## Demo story

`maria` (scripts in `packages/runtime/src/order-agent/story.ts`): María
Fernanda Rojas (synthetic), type 2 diabetes since 2024, HbA1c 6.6 % then
7.1 %, last visit 2025-08-12 where the doctor wrote "Control en 3 meses con
HbA1c". She never came back. The engine reads the note (the configured model,
or the rule-based reader without a key), the deadline watcher turns the
overdue orders into a case, and the agent takes ownership:

1. First contact with two slots (Tuesday first).
2. María: "Ya me hice el examen la semana pasada, pero el martes no puedo" →
   new slots without Tuesday, and an invitation to send the report.
3. "La 2 me sirve" → booked; the engine closes the visit order
   (`Appointment` with the case as origin).
4. A photo of the report (HbA1c 8.4 %, ref 4.0–5.6) → the engine closes the
   HbA1c order from the `Observation`; the reviewer reports the HbA1c rise
   and asks the doctor to review adherence at the visit. María only hears
   that her doctor will review it with her.

`maria_urgent` adds the 8.4 % result sent by the lab three days ago, flagged
abnormal: the engine asks for a visit soon (`abnormal_result_followup`). The
reviewer's findings reach the doctor first, with the engine's request as
"Abnormal result: confirm a follow-up visit?"; meanwhile the agent pursues
only what the doctor wrote (the control and the HbA1c, routine track). Once
the doctor confirms, the agent runs the urgent track (the contact cap is per
patient, so the routine first contact counts toward it). The sample photo and voice notes
are in `packages/runtime/assets/order-agent/` (the scripted readers know them
by sha256; with a key, Muse Spark and Muse Voice read the same files).

## Recording a live run

`apps/api/src/test/agent-live-runs.ts` drives the paths of the evidence
pack (confirmation, reschedule, a photo the engine closes, an abnormal
result for the doctor, a voice note, the no-response ladder, an
undelivered message) against a running demo server in live mode, then
saves each run's export as JSON and a readable Markdown transcript (every
model call with its model, tokens and cost as the gateway logged it,
every tool call with its arguments and outcome, the engine's events):

```sh
node --experimental-strip-types --no-warnings=ExperimentalWarning \
  apps/api/src/test/agent-live-runs.ts --base http://localhost:4391 \
  --code prueba-local-2026 --out docs/evidence/agent-runs/$(date +%F)
```
